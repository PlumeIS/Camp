# Camp 阵营管理

面向 Paper 1.18.2、Java 17。成员、权限、申请状态和阵营属性仍保存在主记分板的 Team Entry 中。

## 项目结构

| 路径 | 职责 |
| --- | --- |
| `Camp.java` | 插件生命周期、阵营加载与查找 |
| `camp/` | `CampInfo`、成员权限和加入规则 |
| `commands/CampCommand.java` | 命令校验和业务操作；UI 复用这些操作 |
| `ui/` | 通用 54 格箱子菜单、分页、层级返回、输入和阵营菜单 |
| `requests/` | 待审核申请的登录、日切和即时提醒 |
| `storage/` | 申请理由及完整日志的异步持久化 |
| `export/` | 主线程数据快照、异步 Excel 导出 |
| `src/test/` | 旧数据、权限、提醒、UI、持久化和导出回归测试 |

## 使用

玩家输入 `/camp` 或 `/camp ui` 打开首页；`/camp ui <阵营ID>` 直接进入成员预览。`/camp help` 查看命令帮助，原有命令继续可用。

- 所有箱子均为 54 格，最上、最下各一整行无 lore 灰色玻璃板；中间有 27 格分页内容和一行导航。
- 首页阵营物品显示信息和属性，左键进入成员预览，右键进入临时日志。成员预览使用带玩家档案的头颅，显示名称、在线状态和权限层级。
- “阵营操作与属性”提供加入、离开、邀请、申请审核、黑名单、名称、颜色、加入规则和解散等功能。点击成员头颅可执行权限调整、拥有者转让、踢出及黑名单操作；OP 另有强制添加和移出功能。
- 修改阵营颜色仅限 OP，非 OP 的拥有者或管理员即使获得 `camp.modify.color` 也不能修改；该节点默认仅 OP，修改颜色按钮只对 OP 显示。命令和 UI 只能选择 Minecraft 的 16 种队伍颜色，UI、导出、聊天及操作日志显示颜色名称（如 `red`、`dark_blue`），不显示 HEX；未设置颜色时显示 `white`。不接受 HEX、自定义颜色或 `reset`、`bold` 等格式名称。
- 创建、名称、申请理由和密钥采用聊天输入，输入 `cancel` 或 `取消` 返回，120 秒未输入则超时。重新执行 `/camp ui` 也会取消输入。文字作为完整参数传入业务层。
- 转让拥有者需在 20 秒内确认；解散、离开、踢出和拉黑等操作提供确认页。
- 登录、插件启用、所在世界游戏天数改变及新申请提交时，有审核权限的阵营管理员收到理由和可点击的 `[接受]`/`[拒绝]`。按钮独立检查相应权限；执行命令时再次校验。
- 头颅优先使用在线玩家或缓存档案；缺失皮肤在异步任务中补全，完成后更新已打开菜单。离线服务器或皮肤服务不可用时可能显示默认皮肤。

普通玩家默认拥有 `camp.ui`。导出使用 `/camp export`，需要 OP 或 `camp.export`（默认 OP）。每次同时生成完整表和玩家公示表，文件保存到服务器的 `plugins/Camp/exports/`，命令会分别报告两个文件的完整路径。

两份 Excel 各有一个工作表，都按阵营颜色填充行，表头和数据均水平、垂直居中。公示表按同一阵营的成员行数纵向合并 `id`、`名称`、`颜色`、`加入条件` 四列，成员和身份逐人显示；完整表合并阵营 ID、名称、颜色、加入规则、阵营属性，玩家 UUID、权限、状态、申请理由等个人数据仍逐人保留。只有一行的阵营保留普通单元格，空阵营保留一行。

- 完整表 `camps-all-日期-序号.xlsx`：包含阵营 ID/名称/颜色、玩家名/UUID、成员状态、数字权限层级、各权限标记、加入规则、申请理由和 Camp 属性。包括待审核玩家和黑名单，保留加入密钥值供管理使用。
- 公示表 `camps-日期-序号.xlsx`：仅有 `id`、`名称`、`颜色`、`加入条件`、`成员`、`成员身份` 六列。只列正式成员，每人一行，身份为拥有者、管理员或成员。加入条件仅说明管理员审核、自由加入或需要密钥，不公开密钥值、UUID、申请理由、待审核玩家和黑名单。

所有阵营都会出现；没有正式成员的阵营在公示表中保留一行，成员和身份留空。日期格式为 `yyyyMMdd`，两份文件共用当天的序号，例如 `camps-all-20261014-1.xlsx` 与 `camps-20261014-1.xlsx`。同一天后续导出按现有两类文件的最大序号递增，重启后继续编号，换日从 1 开始，不覆盖旧导出。两份表使用同一次主线程快照，先完成生成再发布；生成失败会清理本次文件。

UI、导出和聊天仅展示 Camp 相关信息；阵营属性仅包括名称、ID、颜色、加入规则及密钥设置，不展示原生 Team 的碰撞、隐身队友可见性、友伤、前后缀、各 Option 或未知 Entry。公开预览和日志不显示密钥值。隐藏属性仍保留在原有 Team 中。

## 数据兼容及持久化

加载旧 Team 不批量改写 Entry。原有玩家名、`permission.owner.<UUID>`、`permission.admin.<UUID>`、`permission.member.<UUID>`、`permission.idle.<UUID>` 和旧加入规则都可读取，普通成员权限和单一申请状态继续写入原格式，也支持读取此前带阵营标识的权限 Entry。

同一记分板的同名 Entry 只能属于一个 Team。为避免同一玩家在多个阵营中的黑名单互相覆盖，新黑名单使用 `permission.black_list.<阵营ID的Base64URL>.<UUID>`；加入规则新写入 `camp.invite_rule.<规则>@<阵营ID的Base64URL>[.<密钥>]`。这些仍是原 Team 内的 Entry；旧黑名单与旧规则保留读取兼容。未知属性 Entry 保留。成员仍只能属于一个阵营，每名玩家最多一份待处理申请；强制转阵营会清除旧权限，拥有者须先转让或解散。

`plugins/Camp/data/` 只保存补充数据，不替代 Team：

- `<阵营ID的Base64URL>.yml`：待处理申请的理由，原子替换。
- `<阵营ID的Base64URL>.log`：UTF-8 完整操作日志，每行是毫秒时间戳、制表符及 Base64 编码的消息。编码支持理由中的换行和制表符。
- `archive/`：解散阵营的旧日志和理由文件。重建相同 ID 的阵营不会继承旧补充数据。

日志由单写入线程顺序追加，正常关闭时等待写入完成。重启时读取最近 `logs.preview-limit` 条记录（默认 200）到 `CampInfo.tempLogs`，永久文件保留全部记录；损坏日志行会告警并跳过。升级前没有记录过的操作及申请理由无法追溯，旧申请显示“未填写理由”。主记分板的持久化继续由服务器负责。

## 构建与检查

```text
mvn test
mvn package
```

产物：`target/Camp-1.0.0.jar`。JUnit/Mockito 仅为测试依赖，不包含在插件 JAR 内。编译使用 `--release 17`。

编写前核对了缓存中的 Paper 1.18.2 API 源码和对应官方文档；编写后通过同一版本 API 编译、自动回归测试，并使用独立 openpyxl 读取生成的 Excel 验证单表、文本、颜色、筛选和冻结表头。

- [Paper 箱子创建与 Component 接口](https://jd.papermc.io/paper/1.18.2/org/bukkit/Bukkit.html)
- [InventoryClickEvent：界面切换须安排到下一 tick](https://jd.papermc.io/paper/1.18.2/org/bukkit/event/inventory/InventoryClickEvent.html)
- [Paper 玩家档案：皮肤补全需要异步执行](https://jd.papermc.io/paper/1.18.2/com/destroystokyo/paper/profile/PlayerProfile.html)
- [Team Entry 和属性接口](https://jd.papermc.io/paper/1.18.2/org/bukkit/scoreboard/Team.html)

自动测试使用模拟 Bukkit/Paper 接口，未启动真实服务器。部署后的实服验收：

1. 用旧世界加载插件，检查原成员、拥有者、管理员、黑名单和加入规则。
2. 普通玩家提交带理由的申请，让管理员重新登录，并用 `/time add 24000` 触发日切；点击审核按钮，检查权限不足和已处理申请。
3. 检查左右键预览、分页、返回、头颅皮肤、各命令对应的界面操作和聊天输入。尝试 Shift、数字键、双击、丢弃及拖拽，确认不能取走或塞入界面物品。
4. 正常停止后重启，检查申请理由、临时日志；解散后重建同名阵营，确认不会恢复旧日志。
5. 执行导出，用 Excel 打开两份文件，检查颜色名称、填充颜色、空阵营、各权限层级和属性；公示表应只有六列及正式成员，且无密钥、UUID、理由或黑名单。再次导出并重启后导出，确认两个文件共用递增序号且旧文件保留。
